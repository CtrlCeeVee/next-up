# Onboarding a New Client

End-to-end procedure for putting a new paying club on the NextUp Sport app and
into billing. Written from the Kowie Pickleball onboarding (2026-10-08); the
record of that run is at the bottom.

All writes go to the production Supabase project `iwmjssxsonuomxqgtlua`, which
the mobile app shares. Read the template rows first, show every write before
running it, and run the setup as one transaction.

## Prerequisites

- **Supabase MCP** configured on this machine (`.mcp.json`, see
  `Docs/HANDOFF.md` section 2). A personal access token gives full write access.
- **Agreement** with Schedule 1 terms. Contract clause 2.2 says setup follows
  signature and receipt of the initialisation fee; if setup runs before the
  signed copy arrives, get it signed before the club's first billed night.
- **Initialisation fee** received (R500 under Schedule 1 v1.0).

## Information to collect from the club

| Item | Goes to | Notes |
|---|---|---|
| Club / league name | `leagues.name`, `billing.clients.legal_name` | |
| One-line description | `leagues.description` | Shown in the app |
| Venue name | `leagues.location` | Required (NOT NULL) |
| Street address | `leagues.address`, `billing.clients.address` | |
| Weekly nights: day, start time | `league_days` | One row per night. No end-time column exists |
| Number of courts, court names | `league_days.total_courts`, `court_labels` | Default labels "Court 1..n" |
| Admin accounts | `league_memberships` | Each person needs an existing app account; look up `profiles.id` by email |
| Check-in method | `league_checkin_verification` | See below |
| Per-player fee | `billing.terms.per_player_fee` | The agreement's worked example is not the fee; confirm it |
| Contact name, billing email | `billing.clients` | |
| Invoice code | `billing.clients.code` | Short and unique; becomes the invoice prefix (`KP-2026-10`) |
| Contract start date | `billing.terms.effective_from` | Nights before it are never billed |

## How the app uses these tables

Verified against the backend repo (`CtrlCeeVee/next-up-backend`, branch
`origin/production`), not the stale local `main`.

- **League nights are generated by the backend**, not the database.
  `EventWorker` runs every 30 minutes and creates the next occurrence of every
  `league_days` row for every league with `is_active = true`. Nights appear
  within 30 minutes of setup, about a week ahead.
- **`day_of_week`** is 0 = Sunday through 6 = Saturday.
- **Roles**: `league_memberships.role` allows only `player` or `admin` (CHECK
  constraint). Admins manage the league in the app and play free for billing.
- **`leagues.owner_id`** is legacy. The backend never reads or sets it and it
  is nullable. Set it to the NextUp owner account for consistency only.
- **Check-in verification**: no row means `NONE` (pay at the venue, invoice
  later). `PIN` needs PINs generated in `league_checkin_pins` (Northcliff
  only). `PAYMENT` is in-app payment (Pickle View only).
- **`league_billing_accounts`** belongs to in-app payments and is created on
  demand by the app's billing screen. Do not insert it during onboarding.
- **`leagues.matchmaking_system`**: `simple` is what live paying leagues use.
  The backend's own `CreateLeague` defaults to `advanced_v1`; do not use that
  endpoint for onboarding (it also leaves days, memberships and billing unset).
- **`latitude`/`longitude`** default to 0. Set real venue coordinates when
  known; a Google Maps pin on the venue is the reliable source.

## Procedure

### 1. Template read (read-only)

Read an existing paying client as the reference, normally Northcliff Eagles
(`leagues.id = 2`, `billing.clients.code = 'NE'`):

```sql
SELECT * FROM public.leagues WHERE id = 2;
SELECT * FROM public.league_days WHERE league_id = 2;
SELECT c.*, t.* FROM billing.clients c JOIN billing.terms t ON t.client_id = c.id WHERE c.code = 'NE';
```

Confirm each admin's account:

```sql
SELECT p.id, p.first_name, p.last_name, u.email
FROM public.profiles p JOIN auth.users u ON u.id = p.id
WHERE lower(u.email) = lower('<email>');
```

### 2. Agreement on disk

Copy the agreement to `Docs/Billing/agreements/NextUp-<Club-Name>-Agreement.docx`
(replace with the signed copy when it arrives). The folder is gitignored: agreements hold bank and signatory details and the repo is public, so they stay local. `billing.clients.agreement_ref`
points at this path.

### 3. Setup transaction

One transaction: league, nights, admins, billing client, terms. Add a
`league_checkin_verification` insert only if the club uses `PIN` or `PAYMENT`.

```sql
BEGIN;
WITH l AS (
  INSERT INTO public.leagues (name, description, location, address, owner_id, matchmaking_system, latitude, longitude)
  VALUES ('<name>', '<description>', '<venue>', '<address>',
          'c2168748-fe74-4207-ab7f-c691fd0ba837', 'simple', <lat>, <long>)
  RETURNING id),
d AS (
  INSERT INTO public.league_days (league_id, day_of_week, start_time, total_courts, court_labels)
  SELECT l.id, x.dow, x.t, <courts>, ARRAY['Court 1','Court 2']
  FROM l, (VALUES (<dow>,'<HH:MM>'::time), (<dow>,'<HH:MM>'::time)) x(dow, t)
  RETURNING id),
m AS (
  INSERT INTO public.league_memberships (league_id, user_id, role)
  SELECT l.id, u, 'admin'
  FROM l, unnest(ARRAY['c2168748-fe74-4207-ab7f-c691fd0ba837', '<club admin profile id>']::uuid[]) u
  RETURNING id),
c AS (
  INSERT INTO billing.clients (league_id, code, legal_name, contact_name, billing_email, agreement_ref, address)
  SELECT l.id, '<CODE>', '<legal name>', '<contact>', '<email>',
         'Services Agreement + Schedule 1 v1.0 (Docs/Billing/agreements/NextUp-<Club-Name>-Agreement.docx)',
         '<address>'
  FROM l RETURNING id)
INSERT INTO billing.terms (client_id, per_player_fee, service_fee_pct, effective_from, agreement_version, notes)
SELECT c.id, <fee>, 10, '<contract start>', 'Schedule 1 v1.0',
       'R<fee> per player per league night; 10% service fee, inclusive of VAT if any. Initialisation fee R500 received by EFT on <date> (ref <REF>); paid outside invoicing, not billed.'
FROM c;
COMMIT;
```

### 4. Initialisation fee

The fee is paid up front, before any invoice exists. Do **not** add a `debit`
adjustment for it: adjustments become invoice lines, so the club would be
charged again on its first invoice. Record receipt in `billing.terms.notes`
(internal; never shown on invoices or in the console), as in step 3.

The `debit` procedure in `Docs/BILLING.md` is for a once-off charge that is
billed on an invoice, not one already paid.

### 5. Verify

Read back everything written:

```sql
SELECT * FROM public.leagues WHERE name = '<name>';
SELECT * FROM public.league_days WHERE league_id = <id>;
SELECT m.role, p.first_name, p.last_name FROM public.league_memberships m
  JOIN public.profiles p ON p.id = m.user_id WHERE m.league_id = <id>;
SELECT c.*, t.* FROM billing.clients c JOIN billing.terms t ON t.client_id = c.id WHERE c.code = '<CODE>';
-- after 30 minutes:
SELECT id, date, start_time, status, courts_available FROM public.league_night_instances WHERE league_id = <id>;
```

Manual checks:

1. App: the league appears in the list with venue and address; the next
   nights show with the right times and courts.
2. App: each admin sees admin controls on the league.
3. First night: players can check in in the expected way (no PIN prompt for
   `NONE`).
4. Billing console: the client appears. The first draft invoice is created by
   cron on the 1st of the following month.

### 6. Follow-ups

- Marketing site: add the club to `code/web/src/lib/clubs.ts` (club card and
  page). Never list demo leagues.
- Logo: `leagues.logo_url` is unused so far; image hosting is not settled.
- Replace the unsigned agreement in the repo with the signed copy.
- Commit the doc changes (not the agreement; it stays local).
